# FitLife security and account status

## What this source implements

- **Android Google sign-in:** Android Credential Manager obtains a Google credential and Firebase Authentication verifies it. Google/Firebase ID and refresh tokens stay in native code; they are not sent through the JavaScript bridge. The bridge binds every Firestore operation to the expected and currently authenticated Firebase UID. It does not ask for Gmail inbox access. Google sign-in is not implemented as an embedded WebView popup. The browser/PWA cannot perform the required native sign-in, and an old local access flag is not accepted as authentication.
- **Account-isolated, local-first activity sync:** the first Google account claims the device's previously unclaimed activity; later accounts get separate local partitions and their own Firestore paths. Meals, workouts, weights and moods merge by stable ID; step observations, favorite meals and weekly-plan entries also merge, same-ID conflicts are preserved, and content-specific deletion tombstones prevent stale snapshots from resurrecting the deleted version. Local edits remain on the device while offline and retry after reconnect/foreground. Demo records are not uploaded; existing local sample records are retained on the device during sync. A signed-in user can still use the app offline, but Firebase may require a network connection to renew authentication.
- **Per-device data:** profile, most appearance/preferences, today's water, reminder settings and rest/guided timers are not automatically merged between devices. Profile, settings and today's water have per-device cloud recovery copies; on a fresh device one copy may be restored, not necessarily the newest. The rest timer is local and account-partitioned. Concurrent hydration changes are not summed. Sign-out switches the ordinary UI to a separate local guest; the account data remains unencrypted on the device and can be recovered by someone with device-level access. Use a device lock and be mindful of shared phones.
- **Steps and reminders:** Health Connect is optional and reads this Android profile’s aggregate step data, which may include other apps. Its first connecting FitLife account is locally bound to that Android profile until app data is removed; a later account cannot connect it in the same profile. A day is read only if that account remained connected since local midnight. The phone counter uses physical-activity permission and a foreground service; interruptions, device limitations, time changes and battery policies may undercount. Overlapping source/device totals are never added. Step observations are synced in the same non-end-to-end-encrypted cloud payload and are bounded by the sync limits; native step and reminder files reside in Android app-private, no-backup storage but are not separately encrypted by FitLife. Optional workout/water reminders use inexact local alarms, contain no fitness details, and are not synced. Physical-device behavior has not been verified.
- **Cloud limits:** each device snapshot is limited to 500,000 UTF-8 bytes and a maximum of 10 device snapshots can be merged for an account. If the limit, storage, quota, connectivity, validation or rules checks fail, sync pauses with a message; local data is not intentionally cleared. There is no background sync guarantee. Export an encrypted backup regularly and before uninstalling. Data that has not reached the cloud can be lost if the device is cleared or fails.
- **Deletion is not secure erasure:** deleting an activity entry hides it via tombstones; stale device snapshots may still retain its original contents. Signing out does not delete the Google account or cloud data. There is no in-app cloud-account deletion or secure-wipe workflow; the Firebase project owner must arrange deletion. Do not use the app where regulatory-grade deletion is required.
- **Privacy:** Firebase encrypts data in transit and at rest, but FitLife cloud data is **not end-to-end encrypted**. Authorized project administrators and Google/Firebase infrastructure can access the stored profile and fitness data. Normal on-device WebView storage is not encrypted by FitLife; Android/browser backup settings may also make copies. The public `google-services.json` contains app identifiers/API configuration, not an admin credential or signing key.
- **Encrypted manual backup:** optional file exports use AES-256-GCM, a random salt and IV, and PBKDF2-HMAC-SHA-256 with 600,000 iterations. Passphrases are not intentionally saved; losing one makes that file unrecoverable. Android's document picker handles only encrypted envelopes and asks for no broad storage permission. Import authenticates before writing. Merge keeps the current profile, other preferences and water while merging activity, steps, favorites and plan; same-ID activity conflicts are preserved; replace needs explicit confirmation. Browser storage is not a transactional database, so a failed storage rollback cannot be guaranteed in every failure mode.
- **App boundary:** standalone JavaScript is pinned with a CSP SHA-256 hash; production disallows arbitrary inline scripts, eval, frames, objects and cross-origin script loading. External HTTPS navigation leaves the WebView. The existing `file:///android_asset/index.html` origin and signing identity are retained. GitHub update checks are optional and share ordinary network metadata, not fitness data.

## Deployment and verification still required

The uploaded public Firebase configuration is for project `fitlife-b038b` and package `com.tanish.fitlife`. Its Android OAuth client matches the existing release signer SHA-1; a web OAuth client exists and a public provider probe returned a Google sign-in URI. This does **not** prove an actual Android sign-in succeeds, the Spark plan is selected, the database is present, or production rules are secure.

`firestore.rules` contains the proposed owner-only, default-deny rules. They passed local Firestore emulator tests for owner access, anonymous/other-account denial, validation, size and deletion constraints. **The assistant has not deployed or authenticated against production rules.** The user reported publishing rules, but their deployed contents and actual authenticated access have not been independently verified. The project owner must review and verify both before relying on cloud sync for sensitive data. Replacing database rules affects *all* apps using that Firestore database; merge them carefully if it is shared. See [FIREBASE-SETUP.md](FIREBASE-SETUP.md).

The signed APK build, JVM storage doubles, browser simulation, automated accessibility checks and emulator rules tests are useful but do not replace testing on an actual Android phone: Google sign-in, Android WebView crypto, install-over-update, document picker, account switching, cloud retry, phone steps, Health Connect, notifications, TalkBack and Android Back have not been device-verified. Dependency checks and tests are not an independent penetration test or a guarantee of security.

Real phone-number sign-in requires verified SMS or another supported channel. The selected no-payment option does not provide genuine Firebase SMS sign-in on Spark. No unverified/test number is presented as a secure login, and no paid billing or SMS provider has been enabled by this work.
